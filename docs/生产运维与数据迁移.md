# 生产运维与数据迁移

这些工具可在没有正式域名时先测试。所有示例从仓库根目录执行；生产凭据只放在受限环境文件中，不写进命令或提交到 Git。

**当前 VPS 使用发布目录与外部 PostgreSQL，具体操作以 [现有 VPS 部署说明](../docker/README.md) 为准。** 本文下方 `compose.prod.yaml`、`backup.sh`、`restore.sh` 和 `jaxson-backup.*` 命令适用于新服务器模板，不是当前 VPS 的备份恢复入口。当前使用 `backup-vps-existing.sh` / `restore-vps-existing.sh`；它的完整快照还包含私有 `production.env` 和全局角色备份，必须受限保存并在异地传输前加密。

## 将本地内容迁到生产 CMS

迁移通过 CMS API 完成，不直接复制 SQLite 数据库。支持项目、经历、荣誉技能、AI 知识以及项目引用的上传封面；不导出管理员账号、令牌或 Studio 私有数据。简历 PDF 和页面素材随作品站构建发布，不属于 CMS 导入包。

创建一个不提交的环境文件（例如 `scratch/cms-transfer.env`），设置 `CMS_EMAIL` 和 `CMS_PASSWORD`。源、目标后台账号不同，应分别使用环境文件。

```sh
# 从本地已启动的后台导出，现有文件不会被覆盖。
node --env-file=scratch/cms-transfer.env apps/web/scripts/cms-content.mjs export \
  --url http://localhost:3001 --file exports/local-content.json

# 在生产后台先查看会新增、跳过多少条，不写入任何数据。
node --env-file=scratch/cms-production.env apps/web/scripts/cms-content.mjs import \
  --url https://<API_DOMAIN> --file exports/local-content.json

# 确认导入内容和公开范围后执行。
node --env-file=scratch/cms-production.env apps/web/scripts/cms-content.mjs import \
  --url https://<API_DOMAIN> --file exports/local-content.json --apply
```

重复导入默认跳过已有条目；`--update-existing` 才更新匹配条目。项目按 slug 匹配，其他记录按标题或机构、角色、周期等组合匹配；多条匹配会报错，避免覆盖错误记录。上传封面会取得目标 CMS 的新 ID，不复用源 ID。导入不是跨 HTTP 请求的数据库事务：若中途失败，已完成的记录会保留；默认跳过机制支持继续导入。开始前建议执行下面的完整备份。

导出包包含私有项目和未公开知识，保存权限为仅当前用户可读写；`exports/` 和 `backups/` 均已加入 Git 和 Docker 忽略规则。封面只从所选 CMS 域名下载，单文件最大 25 MB；S3 等独立域名资产暂需先迁回 CMS 或单独处理。

## 语义检索与重建索引

默认 `EMBEDDING_MODE=local`，无需外部服务。要启用语义 embedding，生产环境文件设置：

```dotenv
EMBEDDING_MODE=semantic
EMBEDDING_API_KEY=<单独的 embedding 服务密钥>
EMBEDDING_BASE_URL=https://api.openai.com/v1
EMBEDDING_MODEL=text-embedding-3-small
EMBEDDING_TIMEOUT_MS=5000
```

查询与 worker 使用同一配置，索引记录包含模型标识，只比较同一模型的向量。数据库维度固定为 1536，接口必须返回相同维度的有效向量。接口遵循 [OpenAI embeddings 协议](https://developers.openai.com/api/docs/guides/embeddings)；兼容服务也必须满足当前维度要求。LLM 回答密钥和 embedding 密钥是两个配置，不会自动互相替代。

修改模式、模型或服务地址后，先更新 web / worker 环境，再重建索引：

```sh
docker compose --env-file docker/.env.production -f docker/compose.prod.yaml up -d web worker
docker compose --env-file docker/.env.production -f docker/compose.prod.yaml stop worker
docker compose --env-file docker/.env.production -f docker/compose.prod.yaml --profile maintenance run --rm maintenance
docker compose --env-file docker/.env.production -f docker/compose.prod.yaml start worker
```

维护任务从当前 CMS 读取公开记录，停用旧索引并将重建任务加入队列；CMS 原文不被删除。等待 worker 完成后再验收检索质量。若 embedding 调用失败，worker 重试，最终失败的任务保留错误状态；查询会继续使用本地关键词检索，不将语义与哈希向量混用。重建失败时也应重新启动 worker。

worker 会跳过同一条记录的过期事件，避免旧发布任务在失败重试时覆盖新撤回。维护工具使用当前管理员密码；后台改过密码时同步更新维护环境中的登录凭据。

### 检查索引是否跟上

每次失败都会写入 worker 日志（任务编号、第几次尝试、错误原因）；重试 5 次仍失败时，日志另有一行“gave up”。随时可以查看队列状态：

```bash
docker compose --env-file docker/.env.production -f docker/compose.prod.yaml exec worker node apps/web/scripts/run-index-worker.mjs --health
```

输出待处理、处理中、已放弃的任务数、最早待处理任务的等待秒数和最近一次错误。有已放弃的任务，或待处理任务等待超过 10 分钟时，退出码为 1。处理完原因后重新运行上面的重建索引步骤。

## 完整备份与恢复

```sh
# 包含 PostgreSQL dump、上传文件、元信息和 SHA256 校验。
sh docker/backup.sh /var/backups/jaxson-ai-space

# 替换当前环境前，验证校验值并自动创建新的恢复点。
sh docker/restore.sh /var/backups/jaxson-ai-space/<snapshot-directory> --confirm-replace
```

备份会短暂停止 CMS 和 worker，使数据库与媒体一致；静态作品站继续运行。完成或出错时会尝试恢复服务。只有有 `COMPLETE` 标记且校验通过的快照才能恢复。恢复只允许正常文件和目录，不接受媒体归档中的路径穿越、链接或特殊文件。数据库恢复在单个事务中完成，媒体替换失败时可用自动保留的恢复点再次恢复。

快照包含所有 CMS 数据，应保持私有并另存到服务器之外。环境秘密不包含在快照中，也应另外安全保存。当前工具不自动删除历史快照；需要根据磁盘容量设置保留和异地备份策略。快照记录 PostgreSQL 容器的实际 Compose 项目名，更换项目名时校验会阻止误恢复。恢复工具用于已有、可登录的同名环境；新服务器应先完成环境配置和数据库角色初始化。

安装每日备份定时器前，按实际服务器修改 `docker/jaxson-backup.service` 的路径。模板每天北京时间 03:30 起运行，并随机错开最多 15 分钟：

```sh
sudo install -m 644 docker/jaxson-backup.service /etc/systemd/system/jaxson-backup.service
sudo install -m 644 docker/jaxson-backup.timer /etc/systemd/system/jaxson-backup.timer
sudo systemctl daemon-reload
sudo systemctl enable --now jaxson-backup.timer
systemctl list-timers jaxson-backup.timer
journalctl -u jaxson-backup.service
```

## 管理员密码恢复邮件

已接入 [Payload SMTP 邮件适配器](https://payloadcms.com/docs/email/overview)。不配置 SMTP 时不连接测试邮箱；配置后 CMS 的找回密码邮件走指定 SMTP 服务。设置 `SMTP_HOST`、`SMTP_FROM_ADDRESS`，以及需要认证时的 `SMTP_USER` / `SMTP_PASSWORD`。465 使用 `SMTP_SECURE=true`；587 使用 `SMTP_SECURE=false` 并强制 STARTTLS。证书校验保持启用。

修改配置后重建或重新创建 web 服务。`NEXT_PUBLIC_SERVER_URL` 应为真实 CMS 地址，否则邮件中的恢复链接不可用。需要在真实邮箱验收收件、链接地址、令牌有效性及密码修改；本地配置测试不能证明服务商投递成功。

## 配置与验收

`docker/check-env.mjs` 会拒绝语义模式缺少密钥、不完整 SMTP、非法端口以及无效生产秘密。CI 检查维护 profile、Shell 语法和 Node 脚本语法。正式域名、外部模型 API、SMTP 投递和生产内容仍需提供配置后验收。
