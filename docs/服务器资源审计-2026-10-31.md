# 当前 VPS 资源审计

采样：2026-10-31 23:03～23:10，Asia/Shanghai。对象是现有生产 VPS。按站长要求只读审计；未使用备用 VPS，未停止或重启服务，未修改资源限制、健康检查、数据库或 DNS。

## 结论

当前最明显的瓶颈是虚拟 CPU 获得运行时间不足，叠加本机多业务竞争。证据不支持“本站 Next.js 进程占满 CPU”“当前正在大量换页”或“磁盘已满”。同时发现 new-api 线程/句柄偏多、量化机器人占用大部分 Swap、部分服务没有显式资源上限，以及频繁的解释器健康探针。这些是需要继续核实的放大因素，不能只靠延长健康检查超时解决。

高 steal 指向虚拟化层调度或配额方向，但仅靠客户机采样不能区分邻居争用、宿主机过载或套餐限速，不能直接断言服务商超售。KVM 对 steal 的定义是 vCPU 未运行的时间，并排除 vCPU 空闲时间，见 [Linux KVM 文档](https://cdn.kernel.org/doc/html/latest/virt/kvm/x86/msr.html#custom-msr-list)。

new-api 的 866 个线程中，861 个处于睡眠、5 个可运行，大部分等待 futex；不能把 866 个线程都当作正在吃 CPU。另有 3,211 个 socket 句柄，匹配到的 TCP 状态包含 61 个 CLOSE_WAIT、16 个 ESTABLISHED。没有读取请求正文、令牌、连接地址或业务日志。当前只足以提出并发/句柄回收排查项，不能断言连接泄漏、攻击或恶意程序。

## 网站与健康检查的直接影响

- 本机回环：作品站首页返回 200，用时约 4.10 秒；CMS 作品接口返回 200，用时约 11.19 秒。
- 从站长电脑经公网：作品站首页 200，约 4.60 秒；CMS 作品接口 200，约 13.61 秒。每个地址仅请求一次，没有做压力测试；公网时间还包含客户端网络与 Cloudflare。
- Docker 实时 inspect 确认本站 web、worker、portfolio 和 PostgreSQL 均 running/unhealthy，RestartCount 全为 0。各自最近 5 次健康检查全部超时，ExitCode -1，没有连接拒绝特征。不能把它们描述成进程崩溃或反复重启，也不能因为 HTTP 偶尔 200 就视为健康。
- Docker daemon/containerd 的 systemd 状态均 active；Docker socket ping 曾成功，但一次容器列表查询超过 18 秒。管理操作同样受影响。
- SalesPilot core/gateway 每 10 秒启动 Python/urllib 探针，超时 3 秒；其数据库每 5 秒运行 pg_isready，超时 3 秒。CPU 严重争用时，这些探针及容器 exec 的启动开销值得排查，尚未做前后对照，不能认定其消耗占比。
- 直接读取 Docker 持久化状态文件时健康状态显示 starting，已明确视为滞后信息；最终健康结论采用实时 inspect，不采用该旧值。
