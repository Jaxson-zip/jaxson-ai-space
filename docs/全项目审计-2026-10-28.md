## 1. P1：生产依赖命中已披露的安全公告

**证据**：`apps/web/package.json` / 锁文件使用 Next.js 16.3.0、Payload 系列 3.88.0、sharp 0.34.2。此次 `pnpm audit --prod --json` 返回 90 条公告匹配：critical 9、high 36、moderate 34、low 11，分布在 16 个包。原始结果保留于忽略的 `scratch/audit-dependencies-2026-10-28.json`。

**与本项目相关的核对**：

- [Next.js Server Actions 拒绝服务公告](https://github.com/vercel/next.js/security/advisories/GHSA-p3m5-59mp-jv5r)：16.3.0 在影响版本范围内；项目的 Payload layout 确实声明了 Server Action，生产构建清单含 2 个 Node Action。公告给出的 16.x 修复版本为 16.4.1。本轮未验证是否能绕过生产 Access 触发，不声称已成功利用。
- [Next.js AVIF 图片处理公告](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4)：涉及 Next.js 使用 sharp 的图片优化。项目当前详情图设置了 unoptimized，但这不等于整个优化接口已经禁用；具体输入条件及可达性需继续核对。
- 并非所有 critical 匹配都适用：生产 Docker 为 Linux，Windows 专属公告不能算作已确认的生产漏洞；未发现 `next/og`、`use cache`、Payload `orderable: true` 或自定义保留 JWT claim 映射，相关条件性公告不计作已确认可利用问题。
- [Payload SQL 注入公告](https://github.com/payloadcms/payload/security/advisories/GHSA-pj7x-6wpf-pgvp)需要特定字段及读写权限；当前生产 PostgreSQL adapter 3.88.0 已超过该公告的 Postgres 修复线 3.73.0。不能把本地 SQLite 的版本匹配直接写成生产 PostgreSQL 已存在该漏洞。

**影响**：当前功能测试通过不覆盖依赖的安全缺陷，缺少升级和复扫会把已知风险带入下一次发布。

**建议**：先在本地验证 Next.js 至少 16.4.1、Payload 全套一致升级至至少 3.90.0 的兼容性；继续处理 sharp 等传递依赖并重新审计。以上是已核实公告的最低修复线，不保证只升这两个包就清空其余匹配。不要直接执行不经验证的 audit fix，也不要混用不同版本的 Payload 包。此次未重新读取服务器镜像内的实际安装版本。

## 2. P2：CI 和发布健康检查未覆盖重要路径

**建议**：为 CI 建立隔离的公开页面测试数据，加入公开页浏览器检查及带例外期限的安全门禁；发布增加有明确超时的聊天路径与后台任务健康检查。

## 3. P2：CMS 故障被项目详情页误判为 404

**位置**：`apps/web/src/features/portfolio/data.ts:140`、`apps/web/src/app/(frontend)/projects/[slug]/page.tsx:27`。

**复现**：数据加载器在数据库故障时返回 `projects: []`、`isLiveDb: false`；详情页仅判断是否找到项目，随后调用 notFound()。隔离探针 mock 了故障结果，确认组件抛出 `NEXT_HTTP_ERROR_FALLBACK;404`，未访问数据库。

**影响**：临时服务故障会告诉访客和搜索引擎“项目不存在”，也没有服务恢复后的重试体验；metadata 查询存在相同区分缺失。

**建议**：区分“查询成功但无此项目”和“数据不可用”。前者才返回 404；后者走服务错误与可重试状态。

## 4. P2：演示视频静态服务不支持 Range

**位置**：`apps/portfolio/scripts/serve.mjs:55` 至文件读流部分。

**复现**：本地请求演示视频，带 `Range: bytes=0-15`，实际返回 HTTP 200、Content-Length 3892093，没有 Content-Range / Accept-Ranges，并准备发送整段文件。

**影响**：浏览器无法向该源站按所需片段读取视频，弱网或更长的视频可能需要等待完整下载才能顺畅定位。本项不代表当前小视频完全无法播放；未将本地现象直接推断为 Cloudflare 边缘一定返回相同结果。

**建议**：实现合法单段 Range 的 206、越界 416、相应 HEAD/缓存行为，并验证拖动播放；此次不改动视频剪辑或内容。

## 5. P2（设计风险）：CMS 的项目私有状态不保护上传附件

**位置**：`apps/web/src/collections/Media.ts:10`、`apps/web/src/collections/Projects.ts:98`、`apps/web/src/middleware.ts`。

- Media 的 read 始终为 true，匿名媒体查询被中间件明确允许。项目设置 private 不会自动使其封面和视频变成私有资源。
- 项目 visibility 默认 public，没有独立草稿发布阶段；新项目第一次保存即可能公开。
- 本次线上匿名 `/api/media?limit=1&depth=0` 返回 200、totalDocs=0，未发现已经公开的媒体记录；匿名查询 private 项目返回空列表。这里报告的是上传后的边界和操作风险，不是已经发生的数据泄露。

**建议**：明确媒体均公开的产品限制，或增加与引用项目一致的媒体读取权限并覆盖文件下载；新项目改为默认私有，并明确发布操作。不要只隐藏列表而保留可直接下载的私有文件。

## 6. P2：旧版 Word 简历仍作为公开静态文件交付

**证据**：线上两个历史 DOCX 路径仍返回 200、30539 字节、`Cache-Control: public, max-age=14400`；本地 `apps/web/public/resume/`、`apps/web/public/assets/` 中也仍有对应文件。只核对状态和大小，没有读取文档正文。

**影响**：它们不受现行 PDF 更新影响，仍可通过旧链接传播；目前未核对 DOCX 的事实是否与新 PDF 一致，不能宣布内容已统一。

**建议**：确定唯一简历交付入口；旧文件选择重定向、撤回或同步更新，同时处理浏览器和 CDN 缓存。此次未删除文件。

## 7. P2（资源边界缺口）：公开聊天接口先读完整 JSON，再做字符预算校验

**位置**：`apps/web/src/app/api/chat/route.ts:79`、`docker/Caddyfile`。

**证据**：代码先 req.json()，之后才执行消息长度及总字符验证；仓库代理配置没有 request_body 字节上限。单次本地 256 KiB 测试得到业务校验 HTTP 400，而非提前的字节限制拒绝。

**影响**：请求体的接收和解析成本发生在业务预算检查之前；内存中按 IP 的 20 次/分钟限制，也没有覆盖多 IP 总并发。此次未进行大流量、内存耗尽或生产攻击测试，不能据单次 256 KiB 请求声称已能打垮服务器。

**建议**：在代理与应用层增加合理字节上限，读取过程中也检查实际字节，覆盖无 Content-Length/分块请求；再限制全局生成并发，保留现有访客 IP 限流。

## 8. P2（协议兼容）：首页不能解析 CRLF 分隔的 SSE

**位置**：`apps/portfolio/index.html` 的 `buffer.split('\n\n')` 和事件行解析。

**复现**：独立浏览器上下文拦截测试回答，返回 CRLF 格式的 text 与 done 事件。首页没有显示答案，最终提示“暂时没能生成回答，请重试”。探针位于忽略的 `scratch/audit-sse-framing.mjs`；正式全屏页已有独立增量 SSEParser。

**影响**：两处聊天客户端的协议处理不一致。当前自有后端输出 LF，正常链路测试通过；本问题在响应使用 CRLF 时触发，不等于线上每次都出错。

**建议**：统一解析能力，覆盖 LF、CRLF、跨块分隔符、多行 data 及结束事件；避免只改 split 却遗漏行尾 CR 的处理。

## 9. P3：Windows 上微信上下文修补测试仍有 2 项失败

**位置**：`integrations/openclaw/weixin-context.mjs:6`、`weixin-context.test.mjs:6`。

**复现**：集成及通知测试共 29 项，27 通过、2 失败；fixture 经 Windows 检出变为 CRLF，而修补器严格匹配带 LF 的 marker。直接用同一 fixture 原样调用失败，内存中正规化为 LF 后通过。

**影响**：本机无法得到干净的集成回归结果；这是已知的平台兼容问题，不代表 Linux 生产微信插件已坏。

**建议**：在测试 fixture 或文件检出规则中明确行尾，保留对供应商未知代码的拒绝校验，不放宽生产补丁的完整性检查。
