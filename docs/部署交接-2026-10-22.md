## 3. 单独执行数据库迁移（站长确认后）

**为什么要单独做**：新镜像启动时会自动执行未完成的迁移，所以 `deploy-vps-existing.sh` 会先比较数据库里已执行的迁移和发布包里的迁移列表，不一致就拒绝发布（“Migration history differs”）。

**这次迁移只是新增两列**，旧版本代码可以照常运行，所以可以先迁移、后发布：

- `owner.projects.featured`：boolean，默认 false
- `owner.projects.sort_order`：numeric，可为空

步骤：

1. 先做完整备份，并确认备份通过校验（与发布前备份使用同一个工具）：

```bash
sh /opt/jaxson-release-tools/current/backup-vps-existing.sh
```

2. 确认这两列还不存在，迁移也还没记录：

```bash
docker exec jaxson-postgres-prod psql -X -At -U jaxson_admin -d jaxson_release_20261007 -c "SELECT column_name FROM information_schema.columns WHERE table_schema='owner' AND table_name='projects' AND column_name IN ('featured','sort_order')"
docker exec jaxson-postgres-prod psql -X -At -U jaxson_admin -d jaxson_release_20261007 -c "SELECT name FROM owner.payload_migrations ORDER BY name"
```

第一条应无输出；第二条应正好是 `20260909_051231_init`、`20260928_000000_cinematic_project_fields`、`20261007_000000_private_inbox_receipts` 三行。数据库名以 `docker/lib/release.sh` 中的 `JAXSON_DATABASE` 为准。

3. 在一个事务里新增两列并记录迁移：

```bash
docker exec -i jaxson-postgres-prod psql -X -v ON_ERROR_STOP=1 -U jaxson_admin -d jaxson_release_20261007 <<'SQL'
BEGIN;
ALTER TABLE "owner"."projects" ADD COLUMN "featured" boolean DEFAULT false;
ALTER TABLE "owner"."projects" ADD COLUMN "sort_order" numeric;
INSERT INTO "owner"."payload_migrations" (name, batch)
  SELECT '20261022_000000_project_home_order', COALESCE(MAX(batch), 0) + 1 FROM "owner"."payload_migrations";
COMMIT;
SQL
```

4. 验收：重复第 2 步，应看到两列和四条迁移记录；`https://jaxson.bond/` 与 `https://api.jaxson.bond/api/showcase-projects` 仍正常（此时还是旧版本）。

**撤销迁移**（只在应用已回到旧版本时执行）：

```sql
BEGIN;
ALTER TABLE "owner"."projects" DROP COLUMN "sort_order";
ALTER TABLE "owner"."projects" DROP COLUMN "featured";
DELETE FROM "owner"."payload_migrations" WHERE name = '20261022_000000_project_home_order';
COMMIT;
```

## 5. Caddy：让限流拿到真实访客 IP（单独操作）

发布脚本会沿用当前版本的 `Caddyfile`，**不会**使用仓库里的版本，所以提交 `29732b2` 的代理配置需要手动加到服务器上。没加之前功能照常，只是所有访客可能共用同一个 Cloudflare 边缘 IP 的限流额度。

1. 备份当前生效的 Caddyfile（`/opt/jaxson-releases/current/Caddyfile`，以及宿主机 Caddy 实际加载的那份）。
2. 对照仓库的 `docker/Caddyfile`，只合并下面这些内容，不要整份覆盖（服务器上的站点配置可能不同）：
   - 全局 `servers` 中的 `trusted_proxies static private_ranges <Cloudflare IP 段>` 和 `client_ip_headers CF-Connecting-IP`；
   - API 站点的 `reverse_proxy` 中的 `header_up X-Real-IP {client_ip}`。
3. 先 `caddy validate`，通过后再 reload。
4. 验收：用两个不同网络访问 `/api/chat`，在 web 日志中确认两边的 `X-Real-IP` 不同，而且不是 Cloudflare 的 IP 段。
5. 回滚：恢复备份的 Caddyfile 并 reload。
